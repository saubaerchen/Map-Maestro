### Map-Info view panels

- **Position at First Kill** — player positions at FK moment, grouped by timing (<10s / <20s / <30s). Data from analysis JSONs.
- **Position OP-Kill** — sniper kills (Operator + Marshal) by SGE on CT side. Data computed at build time from raw JSONL.
- **All First Kills** — every first kill event on the map, not scoped to timing thresholds.
- **Map Control** — player positioning across 3 time windows into the round.
- **Rotation Patterns** — per-round player trails showing rotations.
- **Retake positions** — CT positions when spike is planted, per site (A/B/C). Site chips are clickable to toggle which sites show.

### JSONL gap: analysis batch fetches matches but does NOT persist them

`analyze_{tag}_early_positioning_batch.py` fetches matches from the API when they are missing from the raw JSONL. It writes the analysis JSON but does **not** append the fetched match to the JSONL. Downstream scripts that read the JSONL directly (agents, map control, defensive bundle sniper data, site-stats) will miss those matches.

**Workaround:** `build_team_site_stats_bundle.py` now includes an API fallback — it cross-references analysis JSONs for match IDs, fetches any missing match from the API, and appends it to the JSONL. **Always run site-stats before agents and map-control** to ensure the JSONL is fully populated first.

### Important: two different map ID fields in raw JSONL

- `matchInfo.map` → human-readable name e.g. `"Lotus"` — **use this one**
- `matchInfo.mapId` → internal Riot code e.g. `"/Game/Maps/Bonsai/Bonsai"` — misleading, ignore

All scripts correctly use `matchInfo.map`. The internal codes (Bonsai, Jam, Foxtrot, Triad, Duality…) do NOT correspond 1:1 to map names and have changed over time.

### Sniper kill data vs early positioning data

- **Early positioning** (first-kill dots) is pre-computed and stored in analysis JSONs — it does NOT need the raw JSONL to display.
- **Sniper kills** are computed at build time by `build_sge_defensive_early_bundle.py` reading the raw JSONL. If the raw JSONL is missing a match, sniper counts will be 0 even if early positioning looks correct.

## Current map pool (as of 2026-06-08)

**Active maps:** Ascent, Breeze, Fracture, Haven, Lotus, Pearl, Split  
**Removed:** Bind (removed from pool ~2026-05)

When adding Ascent data for any team, use the **last 8 weeks** only (no pre-April supplement). Cutoff: `1776038400000` ms (2026-04-13 UTC). Implement via `MAP_DATE_CUTOFFS = {"Ascent": 1776038400000}` in the team's analysis batch script, then add a filter before `selected = target_matches[:TARGET_MAP_COUNT]`.

Ascent coordinate transform — **rotated 90° CW** (PNG is pre-rotated; do NOT add Ascent to `ROTATED_MAPS_CW`):
```python
"Ascent": {"xMultiplier": 7.0e-05, "yMultiplier": 7.0e-05, "xScalarToAdd": 0.426758, "yScalarToAdd": 0.813895, "swap_xy": True}
```
Derivation: for 90° CW rotation, `new_norm_x = 1 − old_norm_y` and `new_norm_y = old_norm_x`. After `swap_xy` (which routes `raw_x→norm_x` and `raw_y→norm_y` in the formula):
- `new_norm_x = raw_x * 7e-5 + (1 − 0.573242)` = `raw_x * 7e-5 + 0.426758`
- `new_norm_y = raw_y * 7e-5 + 0.813895`

Both multipliers are **positive** `7e-5`. The `swap_xy: True` flag swaps `raw_x`/`raw_y` before applying multipliers in `normalize_xy`. All pipeline scripts support this flag: `analyze_*_batch.py`, `build_sge_defensive_early_bundle.py`, `build_retake_postplant_bundle.py`, and `build_map_control_bundle.py` (swap_xy + Ascent transform added 2026-06-23).

The original API transform was `{"xMultiplier": 7e-05, "xScalarToAdd": 0.813895, "yScalarToAdd": 0.573242}` — **do not use these values**; the PNG is now rotated so those constants produce wrong dot positions.

**Note:** `CUTOFF_DATE_MS = 1744934400000` in `analyze_jl_early_positioning_batch.py` is 2025-04-18 UTC (comment previously said 2026 — now corrected). JL's Ascent cutoff is handled by `MAP_DATE_CUTOFFS`, not the global constant.

## Scouting page terminology — always active rules

These rules apply in every session. They exist because past misunderstandings caused features to be built incompletely.

### "Panel" = a named section with a map canvas and dot data

The Map-Info view is made up of **panels**. Current panels per team:

| Panel name | Data source file |
|---|---|
| Position at First Kill (×3 cards) | `defensive-early-data.js` — `thresholds` |
| Sniper Kills | `defensive-early-data.js` — `sniper` |
| All First Kills | `defensive-early-data.js` — `all_fk` |
| Map Control (×3 time windows) | `fks-map-control-data.js` — `mapControl` |
| Rotation Patterns | `fks-map-control-data.js` — `rotations` |
| Retake / Post-Plant | `data/{tag}_{map}_{side}_retake_positions_last3.json` |

The map image with colored dots inside a panel = the **map canvas**.

### Filter scope rule

When Vincent asks to filter or toggle data on the scouting page, **always enumerate every panel currently rendered for that team/view first**, confirm the filter covers all of them, then implement. Do not scope a filter to only the panels already explored in the session.

If Vincent says *"filter every panel on the page"* or *"all panels"* — that means every item in the table above, with no exceptions.

Do **not** interpret *"the maps and tables"* as panel names — that phrase refers to the map canvases and sample chip rows, not the panel list.

### Rotation Patterns data structure

`rotations` in `fks-map-control-data.js` is a **nested list**: each element is a round, and each round is a list of player trails (one per player). Structure:

```
rotations[roundIndex][playerIndex] = { player, snapshots, opponent, date, ... }
```

Filtering by `p.opponent` fails silently when `p` is the inner array. Always read `p[0]?.opponent` when filtering rotation rounds.

### CRITICAL: All data stores must be team-keyed

Any variable that holds team-specific data MUST be keyed by team before map (or use an explicit team guard). The following bugs were caused by violating this rule — they are fixed but must not be reintroduced:

| Variable | Correct lookup | Wrong pattern (never again) |
|---|---|---|
| `allSiteStats` | `allSiteStats[activeTeam]?.[mapName]` | `allSiteStats[mapName]` |
| `allDefensiveRetake` | `allDefensiveRetake[activeTeam][side][mapName]` | (already correct) |
| `mapControlData` | `activeTeam === "eintracht" ? mapControlData : null` | bare `mapControlData` as default |

**Rule:** If you write `fetch('./data/sge_...')` (or any hardcoded team prefix) and store the result without a team key, stop. That's the bug. Every data load that is team-specific must be stored under `data[teamKey]`.

**Team → file prefix mapping** is in `TEAM_FILE_PREFIX` in `app.js`. Use it.

### Sample card HTML is rebuilt in `renderMapInfo`, not `renderDefensivePanels`

`defensiveSampleCard.innerHTML` is set inside `renderMapInfo()`, **after** `renderDefensivePanels()` is called. `renderDefensivePanels` only rebuilds the dot panels.

**Consequence:** Any click handler that calls only `renderDefensivePanels` will update the dots but NOT the floating sample card's button states. To reflect state changes in the card without a full `renderMapInfo` call, manually sync the DOM after toggling:

```javascript
defensiveSampleCard.querySelectorAll("[data-something]").forEach(btn => {
  btn.classList.toggle("active", stateSet.has(btn.dataset.something));
});
renderDefensivePanels(lastDefensiveInfo);
```

This is how the plant site A/B/C buttons work — introduced 2026-06-07.

### Economy filter

All panels (both CT and T) have an economy filter in the floating sample card, below the A/B/C plant site buttons. Key facts:
- **UI layout**: Row 1: `$` `$$` `$$$` (eco/force/full), Row 2: `P` (pistol) `OP` (operator modifier), Row 3: `Enemy ECO`
- **State**: `activeEcoTier` (null | "pistol" | "eco" | "force" | "full"), `activeEcoOp` (bool), `activeEnemyEco` (bool)
- **Tier thresholds** (team avg loadout/player): pistol = roundNum 0 or 12; eco < 2000; force 2000–3799; full ≥ 3800
- **OP modifier**: additive on top of tier — P + OP yields nothing (no OP in pistol rounds, by design)
- **Enemy ECO**: requires opponent tier = "eco" OR "pistol"
- **Filter functions**: `passesEconomyFilter(matchId, roundNum)` and `applyEconomyFilter(items)`
- **Data source**: `{prefix}_economy.json` per team — built by `scripts/build_economy_bundle.py`; preloaded at startup via `preloadEconomyData(teamKey)`; versioned with `ECONOMY_DATA_VERSION`
- Resets on team change, side switch, map change
- Applied to all 7 panel types: thresholds, sniper, all_fk, map control, rotations, retake, +10-20s post-plant

### Plant site filter

T-side panels have A/B/C filter buttons in the floating sample card. Key facts:
- State: `activePlantSites` (a `Set`, max 1 item enforced by click logic — exclusive single-select)
- C-site button only shown on maps in `MAPS_WITH_C_SITE = new Set(["Lotus", "Haven"])`
- Filter function: `applyPlantSiteFilter(items)` — works on both flat arrays (points) and nested arrays (rotation rounds, where `item[0]?.plantSite` is used)
- Resets on team change, side switch, map change
- `all_fk` points include `plantSite` (added 2026-06-07 to `build_sge_defensive_early_bundle.py`); `sniper` points do NOT (CT-side only, no filter needed)

### `updateRotationCardInPlace` must not call `renderMapInfo()` for maps without rotation data

**Root cause of Ascent interactivity bug (fixed 2026-06-12).**

`updateRotationCardInPlace` in `app.js` has a fallback: if `#rotation-panel-card` is not in the DOM, it calls `renderMapInfo()` as a recovery. For any map that has **no rotation/map-control data** (e.g. Ascent for BAR/EP/JL, or any newly added map before rotation data is wired up), this means every player or match button click triggers a full `defensivePanels.innerHTML` replacement, breaking the in-place dot/chip updates and making buttons appear unresponsive.

**Current fix (app.js line ~1119):**
```javascript
if (!card) {
  const hasRotations = (TEAM_MAP_CONTROL_DATA[activeTeam]?.[mapName]?.[side]?.rotations?.length ?? 0) > 0;
  if (hasRotations) renderMapInfo();
  return;
}
```

**Rules:**
- Do NOT revert this to the bare `if (!card) { renderMapInfo(); return; }` pattern.
- When adding a new map that has no rotation data yet, the fix handles it automatically — no additional code needed.
- If you ever add rotation data for a map (e.g. Ascent) later, `buildRotationMarkup` will render `#rotation-panel-card`, and the fallback will never trigger for that map.
- Any regression of "player/match button does nothing on map X" → first check if map X has rotation data in `TEAM_MAP_CONTROL_DATA`. If not, this line is the culprit.

### `allSiteStats` is team-keyed, not map-keyed

`allSiteStats` in `app.js` is a **nested object** keyed first by team, then by map: `allSiteStats[teamKey][mapName]`. File loading uses `TEAM_FILE_PREFIX` to resolve the correct `{prefix}_{map}_site_stats.json` file per team.

**Do not** flatten this to `allSiteStats[mapName]` — that was the bug that caused all teams to show SGE's site stats. When reading or writing `allSiteStats`, always use `allSiteStats[activeTeam]?.[mapName]`.

## VOD Grab workflow

Finds the Twitch VOD URL for a team's matches using VLR.gg + Twitch's public GraphQL API. No credentials needed.

### Steps

1. **Get match list** — fetch `https://www.vlr.gg/team/matches/{id}/{slug}` (not the default team page, which only renders 5 results without JS)
2. **Get match details** — fetch each match page for date + stream channels
3. **Query Twitch GQL** — POST to `https://gql.twitch.tv/gql` with header `Client-Id: kimne78kx3ncx6brgo4mv6wki5h1ko`:
   ```python
   query = '{ user(login: "valorant_emea") { videos(first: 50, type: ARCHIVE, sort: TIME) { edges { node { id title createdAt lengthSeconds } } } } }'
   ```
4. **Match by date** — compare `node['createdAt'][:10]` (UTC date string) to the VLR.gg match date

### Channel priority order
`valorant_emea → valorant_fr → valorant_tur → lvpes2`

### Critical: day-broadcasts contain multiple matches
`valorant_fr` runs long day-broadcasts (4–9 hours) covering several matches. The VOD **title shows one match** but the broadcast contains all matches that day. Do NOT discard a VOD because the title doesn't mention the target team — match by date only.

### Channel coverage patterns (EMEA Challengers 2026 Stage 2)
- **EMEA qualifier playoffs** (May 25–26): `valorant_emea`
- **EMEA Group Stage D** (May 18–22): `valorant_fr` day-broadcasts
- **FR league playoffs** (May 3–12): `valorant_fr` (dedicated per-match VODs with team name in title)
- **FR league group stage** (April weeks 1–4): YouTube only (`VCL FR`) — no Twitch VOD exists

### Output
Excel file `{team}_vods.xlsx` — columns: Map, Game 1 Date, Game 1 Opponent, Game 1 Channel, Game 1 VOD, Game 2 Date, Game 2 Opponent, Game 2 Channel, Game 2 VOD.
